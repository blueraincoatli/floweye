# 技术调研报告：移动端视线检测技术与实现路径

**作者**: MiniMax Agent
**日期**: 2025-06-23

## 1. 研究背景与目标

本项目旨在研究2024-2025年最新的移动端视线检测技术，并结合现有的、基于MediaPipe Face Landmarker V5的技术方案，为“多设备协同视线交互系统”提出最优的MVP实现路径。研究的核心是验证现有方案的健壮性，探索潜在的更优替代方案，并为在无GMS的华为设备上的部署提供明确的技术指引。

## 2. 现有技术方案分析

经过对内部技术文档的深入分析，现有方案具备以下核心特点：

*   **架构成熟**：采用客户端（原生Android/iOS）+协调器（Flutter）的分布式架构，通过MQTT进行本地网络通信，逻辑清晰，职责分明。
*   **算法明确**：核心视线估计算法依赖MediaPipe Face Landmarker V5，通过融合其输出的**头部姿态变换矩阵（facialTransformationMatrixes）**和**眼球相关的Blendshape系数（eyeLook...）**来计算三维视线向量，方法先进且路径明确。
*   **适配方案具体**：针对在无GMS华为设备上部署的挑战，已形成一套经过深思熟虑的适配策略，包括：
    1.  **强制使用Camera2 API**替代CameraX，以获取更稳定、更精细的摄像头控制。
    2.  **强制使用TFLite CPU Delegate**进行模型推理，以规避GPU/NNAPI在部分华为设备上的兼容性和性能问题。
    3.  **使用`tasks-vision-android`依赖库**，避免对GMS的直接依赖。

## 3. 最新技术发展调研

### 3.1 MediaPipe 最新进展 (2024-2025)

*   **结论**：**MediaPipe Face Landmarker V5 依然是当前最稳定和主流的版本，无需更换。**
*   **调研详情**：
    *   **版本更新**：未发现“V6”或更高版本，`face_landmarker_v2_with_blendshapes.task`模型依然是官方推荐的核心模型。
    *   **更新焦点**：MediaPipe在2024年的主要更新集中在**设备端大语言模型（LLM）的集成**和**C++ API的增强**，而非对Face Landmarker的重大改动。
    *   **华为兼容性**：没有新的官方文档专门讨论在无GMS华为设备上的兼容性问题。这从侧面证实了，社区和开发者依赖原生API和CPU Delegate的策略是当前公认的最佳实践。

### 3.2 华为HMS Core替代方案评估

*   **结论**：**不建议更换为HMS Core，坚持使用MediaPipe。**
*   **调研详情**：
    *   **HMS ML Kit & AR Engine**：华为的方案提供了强大的人脸检测和跟踪功能，在华为设备上具有天然的性能优势和兼容性保障。
    *   **关键数据缺失**：然而，HMS Core的API**不直接提供`Blendshape`系数**和**4x4头部变换矩阵**。这两种数据是现有视线估计算法的核心输入。更换为HMS Core意味着需要废弃现有算法，重新探索一套基于不完整数据的、不确定的新算法，开发成本和风险极高。

### 3.3 WebRTC 与 MQTT 通信方案对比

*   **结论**：**维持使用MQTT是更优选择。**
*   **调研详情**：
    *   **WebRTC**：提供理论上更低的P2P延迟，但实现**复杂度极高**（需要信令、STUN/TURN服务器），且其通信模型主要为一对一设计，与本项目的“多对一”星形拓扑不匹配。
    *   **MQTT**：协议轻量、资源消耗低、实现简单，其**发布/订阅模型完美契合**本项目的需求。在本地网络中，其延迟完全可以满足系统小于500ms的响应要求。

### 3.4 开源视线检测替代方案调研

*   **结论**：**坚持使用MediaPipe是最高效、最稳妥的选择。**
*   **调研详情**：
    *   **学术模型**：存在大量开源的视线估算模型，但它们大多停留在算法层面，需要使用者自行完成大量的工程化和优化工作，集成难度和工作量巨大。
    *   **商业/开源SDK**：大部分方案或依赖专用硬件（如Pupil Labs），或已停止独立发展（如The Eye Tribe），或功能和成熟度不足。
    *   **MediaPipe的优势**：MediaPipe提供了**端到端的、高度集成和优化**的框架，其数据丰富性（提供关键点、变换矩阵、Blendshapes的全家桶）和经过大规模验证的鲁棒性，是其他开源方案无法比拟的。

### 3.5 跨平台方案最新进展

*   **结论**：**坚持客户端原生开发是完全正确的决定。**
*   **调研详情**：
    *   无论是Flutter还是React Native，在处理需要高性能、低延迟的实时摄像头数据流时，都面临**原生“桥”带来的性能瓶颈**。
    *   社区的最佳实践普遍指向，当遇到性能问题时，最终解决方案都是**将核心处理逻辑下沉到原生代码中**。因此，直接采用原生开发，从一开始就避免了这些问题。
    *   现有方案中“从Flutter转向原生开发”的决策是富有远见且完全正确的。

## 4. 综合结论与建议

本次技术调研全面地验证了现有技术方案的**健壮性、先进性和可行性**。从核心算法库（MediaPipe）、通信协议（MQTT）到开发模式（原生客户端），当前的选择都是各自领域中最适合本项目需求的。特别是针对无GMS华为设备的适配策略，已经形成了清晰、具体、可落地的最佳实践。

**核心建议**：**应坚定不移地按照现有的技术规划和规格说明推进项目，无需对核心技术栈进行重大调整。** 后续工作的重点应放在高质量的工程实现、细致的性能调优和充分的用户测试上。

# 风险评估与开发计划：多设备协同视线交互系统MVP

> 历史归档说明（2026-04-26）：本文是 2025-06-23 的旧开发计划，其中的角色配置、时间线和技术分工不再代表当前项目进度。当前完成状态请查看 `docs/project_status.md`。

**作者**: MiniMax Agent
**日期**: 2025-06-23

## 1. 潜在技术风险与应对策略

基于技术调研和对现有方案的分析，MVP开发阶段的主要风险集中在工程实现的细节和性能调优上。核心技术选型风险较低。

| 风险类别 | 风险描述 | 可能性 | 影响程度 | 应对策略 |
| :--- | :--- | :--- | :--- | :--- |
| **性能与兼容性** | **中低端华为设备性能不足**：即使使用CPU Delegate，部分老旧麒麟芯片（如710）运行MediaPipe仍可能帧率过低（<15fps），导致交互不流畅。 | 中 | 高 | 1. **严格性能测试**: 在项目初期就在目标低端设备上进行性能基准测试。<br>2. **动态调整参数**: 允许应用根据实际帧率动态降低摄像头输入分辨率或处理频率。<br>3. **算法优化**: 简化置信度计算等后处理逻辑，减少CPU负担。 |
| | **Camera2 API的复杂性**：在不同厂商的设备上，Camera2 API的某些特性（特别是曝光/对焦锁定）可能存在细微的行为差异，导致实现不稳定。 | 中 | 中 | 1. **充分测试**: 在多种品牌和型号的设备上测试摄像头相关功能。<br>2. **封装与抽象**: 创建一个健壮的CameraManager模块，封装所有Camera2的复杂操作，并处理厂商差异。<br>3. **优雅降级**: 如果锁定功能在某设备上失效，应有日志记录并回退到标准的自动模式，保证基本功能可用。 |
| **算法鲁棒性** | **视线判断精度**：在特殊光照（过亮、过暗、逆光）、用户佩戴眼镜（特别是厚镜片或反光镜片）或面部有遮挡时，算法精度可能下降，导致误判。 | 高 | 高 | 1. **数据驱动调优**: 收集在各种挑战环境下的测试视频，用于针对性地调整算法参数（如角度阈值、置信度权重）。<br>2. **用户校准功能**: 在MVP中加入一个简单的用户校准流程，让用户通过注视屏幕上的几个点来微调算法参数，提高个性化精度。<br>3. **明确局限性**: 在产品说明中告知用户当前版本的最佳使用环境和潜在局限性。 |
| | **设备物理参数的确定**：视线判断依赖于对“屏幕目标区域”在相机空间中的位置定义，这个参数的准确性直接影响最终结果。 | 高 | 中 | 1. **简化校准**: 实现一个简单的“首次运行校准”：让用户将面部正对屏幕中心，应用记录此时的头部姿态作为基准，并结合预设的平均屏幕距离来估算屏幕位置。<br>2. **提供手动微调**: 在设置中允许用户手动微调屏幕距离等核心参数。 |
| **开发与集成** | **开发时间估算不准**：Camera2 API和视线检测算法的调试工作量可能超出预期，导致项目延期。 | 中 | 中 | 1. **敏捷开发**: 采用小步快跑的迭代方式，每周设定具体目标并进行演示，及早发现问题。<br>2. **优先完成核心链路**: 优先打通“摄像头 -> MediaPipe -> 视线计算 -> MQTT发送”的核心数据链路，再逐步完善UI和外围功能。 |

## 2. MVP开发时间线估算

假设投入1名资深Android工程师和1名资深iOS工程师，并由1名后端/Flutter工程师负责协调器和MQTT Broker的开发。总时长为**6周**，分为三个主要阶段。

### **第一阶段：核心功能实现 (3周)**

*   **目标**: 完成单平台（优先Android）的核心功能，验证技术链路的完全可行性。

| 周数 | 任务 | 交付物 |
| :--- | :--- | :--- |
| **第1周** | **环境搭建与MediaPipe集成**<br>- 创建原生Android项目，集成MediaPipe依赖。<br>- **实现稳定的Camera2管理**：包括权限、开启、参数配置（分辨率/帧率）。<br>- 运行MediaPipe并成功在回调中获取`FaceLandmarkerResult`。 | - 一个可以实时显示摄像头预览并在Logcat中打印出MediaPipe结果的Android App。 |
| **第2周** | **核心算法与初步UI**<br>- 实现核心的视线估计算法，将MediaPipe结果转换为视线向量和角度。<br>- 开发极简UI，包含“是/否”两个大按钮区域。<br>- 实现简单的屏幕目标位置定义（可暂时硬编码）。<br>- 在UI上初步可视化检测结果（如绘制视线向量或高亮注视的按钮）。 | - App可以在UI上根据用户的注视，大致高亮对应的“是”或“否”区域。 |
| **第3周** | **通信与端到端测试**<br>- 集成MQTT客户端库，连接到测试Broker。<br>- 将视线判断结果（注视目标、置信度）封装成JSON格式并通过MQTT发布。<br>- **协调器（Flutter）**: 开发一个简单的协调器应用，能订阅MQTT消息并实时显示来自客户端的状态。 | - 实现完整的端到端演示：用户注视手机屏幕，协调器应用能实时显示“用户A选择了‘是’”。 |

### **第二阶段：多平台与健壮性 (2周)**

*   **目标**: 完成iOS平台的开发，并提升两个平台的健壮性。

| 周数 | 任务 | 交付物 |
| :--- | :--- | :--- |
| **第4周** | **iOS客户端开发**<br>- 创建原生iOS项目，集成MediaPipe。<br>- **将Android的核心算法逻辑移植到iOS (Swift)**。<br>- 实现iOS的摄像头管理 (AVFoundation) 和MQTT通信。 | - 功能与Android客户端对等的iOS App。 |
| **第5周** | **健壮性优化与协调器增强**<br>- **Android/iOS**: 优化算法，处理边缘情况；实现简单的用户校准功能；完善置信度计算逻辑。<br>- **协调器**: 优化多设备协同决策逻辑（处理冲突、设备离线等）。 | - 客户端在不同光照和姿态下表现更稳定。<br>- 协调器可以同时处理2-3个客户端的状态并做出正确决策。 |

### **第三阶段：整合、测试与交付 (1周)**

*   **目标**: 完成最终的整合测试，准备交付MVP版本。

| 周数 | 任务 | 交付物 |
| :--- | :--- | :--- |
| **第6周** | **整合测试与文档**<br>- 在多台真实设备（包括目标华为手机）上进行端到端的协同测试。<br>- 进行性能分析和最终的参数调优。<br>- 修复Bug，完善UI细节。<br>- 撰写简要的用户手册和部署说明。 | - 一套稳定可运行的MVP系统（包含Android客户端、iOS客户端、Flutter协调器）。<br>- 完整的项目文档。 |

# FlowEye 轮播交互设计方案（双设备约束）

> 状态说明（2026-04-26）：本文是扫描交互设计参考。文中关于“建议新增 `scanning_coordinator.py`”“阶段一/二/三”的计划性内容已有部分实现，不应再视为当前任务清单。当前状态以 `docs/project_status.md` 为准。

> 基于"仅两台旧手机"这一现实约束的务实交互设计。不接受更多设备的假设。

---

## 一、约束声明

本方案严格基于以下现实约束：

- **终端设备 = 2台旧手机**，一台代表"是"，一台代表"否"。
- **患者状态**：可能无法说话、无法动手、可能无法阅读、可能头部转动范围极小。
- **部署环境**：家庭病床或普通病房，无专用支架，充电条件有限。
- **认知水平**：不能假设患者能理解复杂编码或记住多级菜单层级。

**结论**：任何需要3台及以上设备、需要患者精确控制注视时长、需要患者学习编码规则、或需要3级以上菜单层级的方案，均不可行。

---

## 二、核心交互范式：时间轴轮播（Scanning）

### 2.1 基本原理

两台手机永远只显示"是"和"否"。信息输出完全依赖**协调器的TTS语音 + 屏幕大字**。

协调器按顺序播报选项，每个选项停留固定时间。患者听到自己想要的选项时，看向"是"手机。不想要就等它过去，或看向"否"手机跳过。

```
协调器TTS："您渴吗？需要喝水吗？"
    ├── 患者注视【是手机】→ 记录需求：喝水 → 通知家属
    └── 患者注视【否手机】或 5秒无响应
            ↓
协调器TTS："您疼吗？"
    ├── 患者注视【是手机】→ 进入"疼痛"子菜单
    └── 患者注视【否手机】或 5秒无响应
            ↓
协调器TTS："您想翻身吗？"
    ...
```

### 2.2 为什么选轮播？

| 备选方案 | 排除原因 |
|---------|---------|
| 二进制拼字（多次是/否拼出字母） | 拼"水"需要点击十几次，失能患者无法承受 |
| 注视时长编码（看2秒=是，5秒=紧急） | 患者无法精确控制眼球停留时间，误判率极高 |
| 头部姿态辅助（点头/摇头） | 大量失能患者头部无法活动，且算法在大角度下精度下降 |
| 眨眼光标 | 患者可能无法自主控制眨眼，且左右眼区分不稳定 |
| 3台以上设备直接选择 | 违反本方案的核心约束 |

**轮播是AAC（辅助替代通信）领域在单/双键输入场景下的标准范式**，经过数十年临床验证。

## 三、菜单树结构设计

### 3.1 铁律：最多2层

患者不能也不应该记住自己在第几层。超过2层就会迷失。宁可增加第一层的大类数量，也不要做第三层。

### 3.2 推荐菜单树（默认配置）

```
根菜单（每次开机/超时时回到这里）
├── 1. 不舒服
│   ├── 头疼？
│   ├── 肚子疼？
│   ├── 伤口疼？
│   ├── 胸闷/喘不过气？
│   └── 返回根菜单
├── 2. 身体护理
│   ├── 想翻身？
│   ├── 想上厕所？
│   ├── 身体痒/想擦身？
│   └── 返回根菜单
├── 3. 吃喝
│   ├── 想喝水？
│   ├── 想吃东西？
│   ├── 太烫了？
│   └── 返回根菜单
├── 4. 环境
│   ├── 太热了？
│   ├── 太冷了？
│   ├── 灯太亮/想关灯？
│   └── 返回根菜单
├── 5. 社交
│   ├── 想见家属？
│   ├── 需要护士？
│   ├── 想安静/别吵我？
│   └── 返回根菜单
└── 6. 紧急
    ├── 确认紧急呼叫？（是→立即警报 / 否→返回）
    └── 返回根菜单
```

### 3.3 配置化

不同患者的菜单应不同。例如：
- **术后患者**："伤口疼"优先级提到最前，增加"引流管不舒服"。
- **长期卧床老人**："翻身"和"上厕所"排在前两位。
- **渐冻症患者**：后期可能只需要"疼/翻身/家属/紧急"4个选项。

菜单以JSON/YAML文件配置，启动协调器时加载。

## 四、轮播速度优化（降低等待时间）

纯轮播最大的风险是**慢**。10个根菜单项 × 5秒 = 最坏等待50秒。必须优化。

### 4.1 智能排序（LLM唯一该做的事）

**绝不使用LLM生成患者面对的问题文本**。LLM只做一件事：**根据上下文动态调整轮播顺序**。

排序因子：
- **时间因子**：凌晨3点，"疼/翻身/上厕所"排前3位，"看电视"排最后或移除。
- **历史因子**：患者过去24小时内选择了3次"翻身"，今天"翻身"提升到第2位。
- ** meal因子**：饭后1小时内，"上厕所"优先级上升；饭后2小时，"喝水"优先级上升。
- **环境因子**（如接入温湿度传感器）：室温>28°C时，"太热了"提到第1位。

实现方式：每次轮播开始前，LLM或简单规则引擎输出一个排序后的ID列表。协调器按此顺序轮播。

### 4.2 自适应停留时间

不是每个选项都固定5秒。

| 患者状态 | 停留时间 | 触发条件 |
|---------|---------|---------|
| 快速响应者 | 3秒 | 最近5次选择平均响应时间 < 2秒 |
| 标准响应者 | 5秒 | 默认值 |
| 慢速响应者 | 7秒 | 最近5次选择平均响应时间 > 4秒 |
| 首次使用 | 6秒 | 无历史数据，给多一点时间 |

此外：患者连续2轮都"太慢没赶上"（选项过去了才看"是"），系统应自动延长停留时间并TTS提示"不用急，慢慢选"。

### 4.3 快速通道：紧急呼叫绕过轮播

患者**连续注视"是"手机3次**（每次间隔<2秒），或**持续注视"是"超过3秒** → 立即触发紧急警报，跳过所有菜单。

这是独立并行检测的，与轮播状态机无关。患者不需要在菜单里找"紧急"。

## 五、状态机设计

协调器核心是一个有限状态机，避免逻辑混乱。

```
STATES:
  IDLE          - 待机，等待唤醒（可通过语音唤醒按钮或定时自动开始）
  ROOT_SCAN     - 正在轮播根菜单
  SUB_SCAN      - 正在轮播子菜单
  CONFIRM       - 等待患者确认选择（是/否）
  ALERT         - 紧急警报状态
  WAITING       - 已完成一次选择，等待家属响应（不继续轮播）

TRANSITIONS:
  IDLE --(定时/唤醒)--> ROOT_SCAN
  ROOT_SCAN --(患者选"是")--> CONFIRM
  ROOT_SCAN --(患者选"否")--> ROOT_SCAN（下一项）
  ROOT_SCAN --(全部轮完无响应)--> IDLE 或 自动重播
  CONFIRM --(患者选"是")--> WAITING（或直接进入SUB_SCAN）
  CONFIRM --(患者选"否")--> ROOT_SCAN
  SUB_SCAN --(患者选"是")--> CONFIRM 或 WAITING
  SUB_SCAN --(患者选"否")--> SUB_SCAN（下一项）
  SUB_SCAN --(选"返回"或超时)--> ROOT_SCAN
  WAITING --(家属确认/超时)--> IDLE 或 ROOT_SCAN
  * --(三连"是")--> ALERT
  ALERT --(护士确认)--> IDLE
```

### 5.1 防误触：确认机制

患者注视"是"选中一个选项后，不立即执行。协调器TTS确认："您选择了'喝水'，对吗？"
- 患者再看"是" → 确认执行
- 患者看"否" → 取消，回到轮播

**例外**：如果同一选项在过去1小时内已被患者选择过2次以上，说明是高频真实需求，可跳过确认，直接执行。

### 5.2 超时回退

- 根菜单轮播完一整圈无响应 → TTS："我在等您，需要帮您叫家属吗？" → 再等一轮 → 回到IDLE待机。
- 子菜单10秒无响应 → 自动回到根菜单，避免患者迷失在深层。

## 六、TTS（语音播报）方案

### 6.1 为什么必须

患者很可能：
- 视力模糊或无法聚焦看清屏幕
- 头部无法转动看协调器屏幕
- 不识字

**声音是唯一可靠的信息通道。**

### 6.2 实现

- **协调器端**：Python `pyttsx3` 或系统TTS引擎。承担主要播报职责。
- **手机端**：不需要TTS。患者不需要听手机说什么，只需要记住"左边是是，右边是否"。
- **语音特性**：
  - 语速比正常慢30%
  - 每个选项播报后留 **2秒空白**
  - 深夜模式（22:00-06:00）自动降低音量50%，或切换为耳机输出
  - 支持方言（如患者只懂粤语，TTS应调用对应语音包）

### 6.3 播报内容模板

```
[轮播报选项]: "您{选项内容}吗？需要的话，请看'是'。"
  例："您渴吗？需要喝水的话，请看'是'。"

[确认]: "您选择了'{选项}'，对吗？"

[执行]: "好的，已通知家属：{选项}。"

[等待]: "我在等您，如果不需要，请看'否'。"

[紧急]: "紧急呼叫！紧急呼叫！患者需要帮助！"
```

## 七、协调器端形态建议

### 7.1 不能是命令行

当前的 `simple_coordinator.py` 打印日志到终端，这对家属和护士毫无意义。协调器必须有一个**可视的、能放在患者床头或护士站的界面**。

### 7.2 最低可行形态：Web页面

用 Python + Flask/FastAPI 跑一个**局域网全屏Web页面**。

页面元素：
- **超大文字区域**：当前播报的选项（字号80px+，陪护人员在远处也能看清）
- **状态指示**：当前在第几层、还剩几个选项、患者最后的选择
- **历史记录**：今天患者表达过的所有需求，带时间戳
- **紧急按钮**：护士/家属可以手动标记"已处理"
- **配置入口**：调整菜单、语速、停留时间

任何手机/平板/电脑打开 `http://协调器IP:5000` 即可看到。

### 7.3 更优形态：旧平板Dedicated

如果有第三台旧设备（不用来检测视线，只做显示），把它作为协调器专用显示屏，挂在患者床头。这比Web页面更稳定，不需要家属去打开浏览器。

## 八、通知分级机制

| 级别 | 触发条件 | 协调器端行为 | 家属/护士端 |
|------|---------|-------------|------------|
| **P0 紧急** | 患者触发三连"是"快速通道，或选择了"紧急"并确认 | 全屏红色闪烁 + TTS循环播报"紧急呼叫" + 尖锐提示音 | 立即：微信/钉钉推送 + 声音提醒 |
| **P1 重要** | 患者选择了"疼"、"胸闷"、"喘不过气" | 黄色大条幅 + TTS播报一次 + 柔和提示音 | 10秒内未处理则推送 |
| **P2 一般** | 患者选择了"喝水"、"翻身"、"上厕所"等 | 绿色提示 + TTS播报"已通知：XXX" | 仅在协调器屏幕显示 |
| **P3 信息** | 患者选择了"想安静"、"心情好"等 | 静默记录，不播报 | 仅写入日志 |

**防止通知疲劳**：如果患者5分钟内连续3次选择同一非紧急项（如反复选"喝水"），自动升级为P1并推送，因为可能是真实需求未被满足。

## 九、与现有系统的对接

### 9.1 Android端改动范围

两台手机**几乎不需要改动**。现有代码已经能稳定检测"是否注视本屏幕"。

唯一可能的新增功能：
- **连续注视检测**：协调器需要知道患者是否"连续注视'是'手机超过3秒"，用于紧急快速通道。
  - 现有MQTT消息已包含 `isLookingAtScreen` 和 `timestamp`，协调器端自己计算连续时长即可。**无需改手机端代码**。

### 9.2 协调器端重写范围

- 原 `simple_coordinator.py` 的MQTT接收逻辑保留。
- 新增：状态机、轮播调度、TTS、Web界面、配置加载、通知模块。
- 建议作为一个新文件 `scanning_coordinator.py`，不删除原文件，方便对比和回退。

## 十、风险与应对

| 风险 | 可能性 | 应对 |
|------|-------|------|
| 患者轮播时"追不上"想要的选项 | 高 | 自适应停留时间 + 患者错过2次后自动延长 + 允许"否"回退到上一项（循环轮播时） |
| 患者误触"是"（无意识注视） | 中 | 确认机制（选后二次确认）+ 1小时内重复项免确认 |
| 家属没听到/看到通知 | 中 | 多级通知（屏幕→声音→推送），未处理自动升级 |
| 患者对TTS声音无反应（听力障碍） | 中 | 协调器屏幕大字必须足够大；可考虑配合简单光信号（屏幕颜色变化） |
| 两台手机MQTT不同步 | 低 | 协调器以自身接收到的MQTT时间戳为准做决策，不要求设备间时钟同步 |
| 半夜TTS吵醒陪护 | 中 | 深夜模式自动降音量或切换耳机输出 |

## 十一、实施路径建议

不追求一步到位，分阶段验证：

### 阶段一：最小可行轮播（1~2天）
- 硬编码5~6个根菜单项，无子菜单。
- 固定5秒停留时间，无智能排序。
- 协调器命令行 + TTS（无Web界面）。
- **目标**：验证患者能否理解"听到想要的就看'是'"这个基本逻辑。

### 阶段二：完整菜单 + Web界面（1周）
- 加入2层菜单树（JSON配置）。
- 加入确认机制和超时回退。
- Flask Web界面（显示当前选项和历史记录）。
- **目标**：家属能实际使用，护士能看到患者需求。

### 阶段三：智能优化 + 通知集成（1~2周）
- 自适应停留时间。
- 基于规则/LLM的智能排序。
- 微信/钉钉推送。
- 三连"是"紧急通道。
- **目标**：产品化可用。

---

## 十二、结论

在"只有两台旧手机"的现实约束下，**轮播扫描（Scanning）+ 是/否确认是唯一可行的复杂表达方案**。它牺牲了速度（相比多设备直接选择），但换来了物理部署的可行性。

本方案的核心设计哲学：
1. **患者永远只做"是/否"判断**，不记忆、不编码、不学习。
2. **所有复杂度由协调器承担**（智能排序、层级管理、TTS、通知）。
3. **宁可慢，不要错**：确认机制、超时回退、防误触优先于速度。

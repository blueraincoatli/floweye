# FlowEye 分层交互架构：按设备数量适配

> 核心原则：**设备数量不是门槛，而是能力刻度。** 从 1 台到 N 台，每一层都有完整的表达闭环，只是效率和丰富度不同。

---

## 一、架构总览

| 设备数 | 交互模式 | 患者动作 | 表达效率 |
|--------|---------|---------|---------|
| 1台 | 单键扫描 | 注视 / 不注视 | 1 bit/轮 |
| 2台 | 双键扫描 | 左=是 / 右=否 | 1 bit/轮，意图明确 |
| 2台+ | 成对选择 | 看左 / 看右 | 1 选项/轮（2选1）|
| 3-4台 | 直接选择 | 看对应设备 | 1 选项/轮（N选1）|
| 5台+ | 并行矩阵 | 看对应设备 | 多维度同时表达 |

**关键设计**：系统运行时自动检测在线设备数量，动态切换交互模式。设备离线时平滑降级，重新上线后自动升级。

---

## 二、Tier 1：单设备（1台手机）

### 2.1 核心逻辑

```
协调器播报选项 -> 开启选择窗口（默认5秒）
    |-- 患者在窗口内稳定注视手机 [>1.5秒] -> 判定"是"
    |-- 窗口结束无稳定注视 -> 自动跳过（等效"否"）
```

### 2.2 两种使用场景

#### 场景 A：家属在场 -- 人机混合模式（推荐）

家属坐在床边，看着协调器屏幕或靠自己的判断提问，患者只需回答"是/否"。

```
家属（看着患者）："您想喝水吗？"
        |
患者注视手机 [>1.5秒] -> 协调器记录"喝水"，TTS播报"已通知家属"
        |
患者无注视 -> 家属继续问下一个问题
```

**为什么这是单设备的最佳场景？**
- 家属作为"语义层"，实时判断患者状态（是睡着了？还是在思考？）
- 家属可以灵活调整问题，不需要等待系统轮播
- 单设备的"不注视语义模糊"问题被人类弥补了

#### 场景 B：自动轮播 -- 单键扫描模式

家属不在时，协调器自动 TTS 轮播选项。

```
协调器TTS："您想喝水吗？想的话请看手机。" [窗口开启，5秒]
    |-- 注视 >1.5秒 -> 记录"喝水" -> 进入确认
    |-- 无注视 -> 窗口关闭 -> 播报下一项
```

### 2.3 单设备的关键风险与缓解

| 风险 | 原因 | 缓解策略 |
|------|------|---------|
| 无意识注视误触 | 患者目光偶然扫过手机 | 提高注视阈值至1.5秒；加入确认机制 |
| 无法区分"否"和"无响应" | 睡着了 vs 不想选 | 加入唤醒机制：从待机进入交互需持续注视3秒；长时间无交互自动回待机 |
| 患者思考中错过选项 | 没想好就超时了 | 自适应停留时间；错过2次后自动延长 |
| 无法主动跳过 | 必须等超时 | 缩短默认停留时间至3秒（单设备轮播应比双设备更快） |

### 2.4 单设备的紧急通道

```
患者持续注视手机 >3秒（与正常选择的1.5秒区分）
    -> 立即触发紧急警报
    -> 跳过所有菜单和确认
```

**设计意图**：正常选择是"短暂凝视"，紧急是"长时间凝视"。用时长而非位置来区分。

## 三、Tier 2：双设备（2台手机）

### 3.1 核心逻辑

两台手机空间位置固定：
- **左设备 = "是"**（放在患者左侧）
- **右设备 = "否"**（放在患者右侧）

```
协调器TTS："您想喝水吗？" [窗口5秒]
    |-- 看左设备（是）-> 记录需求 -> 进入确认
    |-- 看右设备（否）-> 立即跳过，播报下一项
    |-- 无响应 -> 超时跳过
```

### 3.2 相比单设备的核心优势

| 能力 | 单设备 | 双设备 |
|------|--------|--------|
| 主动跳过 | 无（等超时） | 有（看"否"设备） |
| 否定意图明确性 | 模糊 | 明确 |
| 紧急通道 | 长时间凝视（易误判） | 三连"是"（清晰） |
| 误触容错 | 低 | 中（需主动转向） |

### 3.3 两种子模式（根据患者能力切换）

#### 子模式 2a：固定是/否（默认）

两台设备永远只显示"是"和"否"。信息完全靠 TTS 输出。

**适用**：视力差、不识字、认知能力较弱的患者。

#### 子模式 2b：成对直接选择（高级）

两台设备显示具体内容，如：
- 第一轮：左屏"喝水" / 右屏"疼痛"
- 第二轮：左屏"翻身" / 右屏"上厕所"

配合 TTS："左边是喝水，右边是疼痛。您需要哪个？"

**适用**：能看清屏幕、有一定认知能力的患者。  
**效率**：一轮呈现 2 个选项，比轮播扫描快一倍。

## 四、Tier 3：3-4台设备（直接选择）

这是原始设计 `interaction_design_proposal.md` 中的主力模式。

### 4.1 核心逻辑

```
协调器TTS："您哪里不舒服？"
    |
设备A[头]  设备B[肚子]  设备C[伤口]  设备D[都不]
    |
患者直接注视对应设备 -> 一步完成选择
```

### 4.2 与轮播扫描的效率对比

假设有 8 个选项，每轮停留 5 秒：

| 模式 | 轮数 | 最坏等待时间 | 患者认知负担 |
|------|------|------------|------------|
| 单设备轮播 | 8 轮 | 40 秒 | 极低 |
| 双设备轮播 | 8 轮 | 40 秒 | 低 |
| 双设备成对 | 4 轮 | 20 秒 | 中 |
| 4 台直接选择 | 1 轮 | 5 秒 | 低（直接看） |

**核心洞察**：设备数量直接决定表达效率，但每一层都是完整可用的。

## 五、Tier 4：5台+设备（并行矩阵）

### 5.1 程度/等级选择

```
协调器TTS："疼痛程度？"
    |
设备1[1]  设备2[2]  设备3[3]  设备4[4]  设备5[5]
```

同理可用于：
- 紧急程度：普通 / 较快 / 立即
- 冷热度：太冷 / 有点冷 / 正好 / 有点热 / 太热
- 情绪：开心 / 平静 / 焦虑 / 痛苦 / 剧痛

### 5.2 多维度并行

```
协调器TTS："请选择您的不适和程度"
    |
左列（部位）：头 / 肚子 / 伤口 / 胸口
右列（程度）：1 / 2 / 3 / 4 / 5
    |
患者先看"头"设备，再看"5"设备 -> 表达"头疼，程度5"
```

**注意**：这要求患者能理解"先选类别、再选程度"的两步逻辑，认知负担较高。仅适合清醒、有一定理解能力的患者。

## 六、智能降级与升级策略

### 6.1 运行时自动适配

```python
# 协调器启动时检测在线设备
online_devices = mqtt_discovery()

if len(online_devices) >= 5:
    mode = "PARALLEL_MATRIX"
elif len(online_devices) >= 3:
    mode = "DIRECT_SELECTION"
elif len(online_devices) >= 2:
    mode = "DUAL_SWITCH"
else:
    mode = "SINGLE_SWITCH"
```

### 6.2 平滑降级场景

| 事件 | 降级前 | 降级后 | 过渡方式 |
|------|--------|--------|---------|
| 设备使用中没电 | 3台直接选择 | 2台双键扫描 | TTS播报：一台设备离线，已切换模式 |
| 夜间仅1台充好电 | 4台直接选择 | 1台单键扫描 | 菜单自动简化为最常用4项 |
| 患者疲惫无法转头 | 2台双键 | 1台单键 | 家属可手动触发单设备模式 |

## 七、总结：什么场景用哪一层？

| 场景 | 推荐层级 | 理由 |
|------|---------|------|
| 只有1台旧手机，家属在场 | Tier 1 + 人机混合 | 单键扫描，家属弥补语义模糊 |
| 只有1台旧手机，家属不在 | Tier 1 自动轮播 | 接受慢速和模糊；选项保持最少（4-6项） |
| 2台手机，患者视力差/不识字 | Tier 2a 固定是/否 | 最稳健，AAC领域临床验证的标准范式 |
| 2台手机，患者能阅读 | Tier 2b 成对选择 | 比轮播快一倍 |
| 有3-4台手机 | Tier 3 直接选择 | 效率最优，原始设计目标 |
| 有5台+手机，患者清醒 | Tier 4 并行矩阵 | 表达最丰富，支持疼痛量表等 |

## 八、待讨论问题

1. **实现优先级**：是四层同时实现，还是先做 Tier 1+2，后续再叠加？
2. **单设备紧急阈值**： prolonged gaze 的 3 秒阈值是否安全？如何避免正常选择被误判为紧急？
3. **成对选择的启用条件**：Tier 2b 是否需要患者/家属显式开启，还是检测到视力良好后自动启用？
4. **3台+设备的物理摆放**：左右很清楚，但3-4台设备在病床上如何排布才能让患者自然注视？

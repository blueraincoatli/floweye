# FlowEye 交互层设计方案建议

> 基于当前已实现的多设备协同视线检测架构，针对"如何帮助患者表达自己"提出的分层交互设计建议。

---

## 一、核心设计原则

在提出具体方案前，先明确几条必须遵守的原则：

1. **认知负担最小化**：失能患者往往伴随认知疲劳、意识模糊，每一步交互都要极度简单。
2. **确定性优于智能性**：医疗场景下，可预测、可验证的交互比"智能但可能出错"更重要。
3. **时间即代价**：患者用眼神操作已经很慢，尽量减少层级和确认次数。
4. **容错第一**：误触、误判必须有优雅的回退机制，不能锁定在死胡同里。
5. **陪护人员是系统的一部分**：设计必须同时服务患者和陪护/护士，不能只考虑患者端。

---

## 二、关键问题：预设提问 vs LLM即时生成？

### 我的明确建议：**以预设决策树为主，LLM仅做智能排序和补全**

| 维度 | 纯预设提问 | 纯LLM生成 | 混合方案（推荐） |
|------|-----------|----------|----------------|
| **延迟** | 极快（本地/缓存） | 几百ms~数秒 | 快（预加载+本地渲染） |
| **可预测性** | 高 | 低（可能生成患者无法理解的问题） | 高（问题库审核过） |
| **个性化** | 低 | 高 | 中高（LLM排序+上下文裁剪） |
| **医疗安全** | 可审计、可验证 | 黑盒，难以追责 | 可审计（LLM不直接生成医疗问题） |
| **离线可用** | 是 | 否（需联网） | 是（核心功能不依赖LLM） |

### 为什么不用纯LLM生成问题？

- **延迟是杀手**：患者注视某个选项后，如果因为等LLM回复而屏幕空白数秒，会产生焦虑和困惑。
- **LLM可能"过度发挥"**：生成"您今天感觉精神状况如何？"这种需要抽象自评的问题，对失能患者太难了。预设的问题应该是"您头疼吗？""您想喝水吗？"这种具体、可立即回答的。
- **医疗合规**：预设问题可以由医护人员审核、定制，LLM生成的问题无法预先审核。

### LLM应该做什么？（而非生成问题本身）

1. **智能排序**：根据时间（凌晨3点优先问"疼不疼"而非"想不想看电视"）、历史记录（患者昨天反复选择了"疼"，今天优先问疼痛位置和程度）、生理信号（如有接入，心率异常时优先问"胸闷吗"）。
2. **上下文补全**：患者选择了"疼" → LLM帮协调器生成下一步追问的逻辑（但追问的问题本身仍是预设模板）。
3. **会话摘要**：将患者一整天的选择记录整理成"患者今日表达摘要"，供护士查房时阅读。
4. **多轮对话管理**：当患者在"是/否"之间犹豫时，LLM判断是否需要回退到上一级菜单，或提供安抚性提示。

## 三、推荐的交互架构：三层模型

```
┌─────────────────────────────────────────────────────────────┐
│                    协调器端 (Coordinator)                     │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────┐   │
│  │   TTS播报    │  │  决策引擎    │  │   通知模块       │   │
│  │  (问题和选项) │  │(预设树+LLM排序)│ │(屏幕+声音+推送)  │   │
│  └──────────────┘  └──────────────┘  └──────────────────┘   │
└──────────────────────────┬──────────────────────────────────┘
                           │ MQTT
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   ┌─────────┐      ┌─────────┐      ┌─────────┐
   │ 设备A   │      │ 设备B   │      │ 设备C   │
   │ [ 水 ]  │      │ [ 疼 ]  │      │ [翻身]  │
   └─────────┘      └─────────┘      └─────────┘
```

### 第一层：直接选择（多选项并行）—— 主力模式

**这是最应该优先开发的交互模式，因为它最充分地利用了你们现有的分布式设备架构。**

- 协调器播报一个问题："您哪里不舒服？"
- 3~4台设备屏幕分别显示：**"头"、"肚子"、"伤口"、"都不"**
- 患者直接注视对应设备，一步选择。
- 协调器检测到注视决策后，TTS确认："您选择了头部，对吗？"
- 再用两台设备做"是/否"确认。

**优势**：
- 把现有"是/否两台设备"扩展到"多选项多台设备"，效率指数级提升。
- 患者不需要记住复杂菜单层级，所有选项同时可见。

### 第二层：是/否确认 —— 辅助模式

保留现有的"是/否"双设备架构，但主要用于：
- 对直接选择的**二次确认**
- 简单的**开关类问题**（"您需要关灯吗？"）
- 从直接选择进入后的**子问题**（患者选了"疼" → "是比昨天更疼吗？"）

### 第三层：程度/等级选择 —— 进阶模式

- 协调器问："疼痛程度？"
- 5台设备显示：**1、2、3、4、5**
- 患者注视对应数字。
- 同理可用于：冷热度（1-5）、紧急程度（普通/较快/立即）。

## 四、TTS（语音播报）：不是"要不要"，而是"怎么做"

**结论：TTS是必须的，且患者端和协调器端都需要。**

失能患者群体中，有大量情况是：
- 视力严重受损或无法聚焦阅读
- 意识清醒但无法转头看屏幕
- 识字能力有限（老年患者）

因此，**所有文字必须有声音**。具体实现建议：

### 患者端（Android设备）
- 使用 Android `TextToSpeech` API。
- 设备被患者注视时，**朗读自己的标签**（如患者看向"水"设备时，该设备播报"水"）。
- 这样即使患者看不清屏幕上的小字，也能通过声音确认自己注视的是正确选项。
- 声音应温和、清晰，音量适中（深夜模式可降音量或改用震动）。

### 协调器端
- 必须承担**主要播报职责**：朗读当前问题、朗读患者的选择结果。
- 让房间里的陪护人员也能听到交互过程，不必盯着屏幕。
- 患者做出紧急选择（如"呼吸困难"）时，协调器应发出**明显不同的警报音+语音**（"患者需要紧急帮助"）。

### TTS节奏设计
- 问题播报后，留出 **3~5秒空白**，让患者理解并开始移动视线。
- 设备被注视时，**不要立即朗读**（避免患者在移动视线过程中被连续播报干扰），等注视稳定500ms后再播报。
- 支持"重复播报"功能：患者长时间无响应时，自动重复一次问题和选项。

## 五、如何通知陪护人员和护士？

建议设计**分级通知机制**，不能所有需求都用一种方式通知，否则护士会疲劳性忽略。

### 通知分级

| 级别 | 患者选择示例 | 协调器端行为 | 护士/陪护端通知 |
|------|-------------|-------------|----------------|
| **紧急** | "呼吸困难"、"剧烈疼痛"、"掉下床了" | 全屏红色闪烁 + 尖锐警报音 + TTS循环播报 | 护士站蜂鸣器 / 微信企业号推送 / 短信 |
| **重要** | "疼痛"、"想翻身"、"要上厕所" | 黄色提示条 + 柔和提示音 + TTS播报一次 | 协调器屏幕置顶显示 + 可选的APP推送 |
| **一般** | "想看电视"、"想喝水"、"太热了" | 绿色提示 + TTS播报 | 仅在协调器屏幕记录，不主动打扰护士 |
| **信息** | "心情好"、"不想说话" | 静默记录 | 仅写入日志，供查房时查看 |

### 通知渠道建议

1. **协调器本机**：必须有大而明显的视觉反馈（不能只是命令行打印）。建议把协调器升级为带GUI的界面，或至少是一个Web页面。
2. **护士站**：如医院已有护士呼叫系统，协调器可通过继电器或API对接。如无，可用一个专用的Android平板放在护士站，作为"护士端接收器"。
3. **移动推送**：企业微信/钉钉/飞书的群机器人Webhook，低成本且可靠。家属也可以加入群组，了解患者需求。
4. **声音提示**：不同级别用不同的提示音。紧急级别可以用医院现有的呼叫铃声。

## 六、协调器端的必要升级

当前的 `simple_coordinator.py` 是一个命令行工具，这对于实际使用是不够的。协调器需要承担"交互大脑"的角色，建议升级为以下形态：

### 功能需求

1. **问题调度引擎**
   - 维护一个预设问题树（JSON/YAML配置）。
   - 根据患者上一次的选择，决定下一次问什么。
   - 支持"超时回退"：患者30秒无响应，自动回到根菜单或重播当前问题。

2. **TTS引擎集成**
   - 接入 `pyttsx3` 或系统TTS。
   - 支持语速、音量调节。

3. **Web界面**
   - 用 Flask/FastAPI 快速搭建一个局域网Web页面。
   - 显示：当前问题、设备状态、患者选择历史、紧急事件队列。
   - 护士可以通过Web页面手动触发问题（如"该吃药了，您准备好了吗？"）。

4. **通知模块**
   - 可配置的Webhook推送。
   - 本地声音播放（Windows/MediaPlayer 或 pygame.mixer）。

5. **数据记录**
   - 记录每次交互的时间戳、问题、选择、置信度。
   - 生成日/周报告，供医生了解患者表达频率和主要诉求。

## 七、渐进式实施建议

不建议一次性做完整套系统，建议分阶段：

### 第一阶段（立即做）：多选项直接选择 + TTS
- 将现有2台设备扩展到3~4台设备。
- 协调器端硬编码一组最常用的需求（水、翻身、疼痛、家属）。
- 给每台设备和协调器加上TTS。
- 这就是最实用的"表达板"，患者已经可以表达80%的日常需求。

### 第二阶段（1~2周后）：决策树 + 确认机制
- 患者选择"疼痛"后，协调器追问"头部？肚子？伤口？"。
- 加入"是/否"确认步骤，降低误操作。
- 协调器升级为带Web界面的版本。

### 第三阶段（1月后）：通知集成 + LLM辅助排序
- 接入微信/钉钉推送。
- 接入护士呼叫系统。
- 引入LLM做问题排序和会话摘要（本地部署小模型如Qwen/ChatGLM，或调用云端API）。

## 八、总结

| 问题 | 建议 |
|------|------|
| **如何帮助患者表达** | 以**多设备直接选择**为主（3~5个选项同时呈现），**是/否**为辅做确认，支持**程度选择**。这是现有分布式架构的最优利用方式。 |
| **预设 vs LLM** | **预设决策树为主**，LLM只做排序、摘要、上下文管理。绝不直接用LLM生成患者面对的问题。 |
| **TTS** | **必须做**。患者端（注视时朗读标签）+ 协调器端（朗读问题和结果）。 |
| **通知护士** | **分级通知**：紧急（多渠道强提醒）/ 重要（屏幕+声音）/ 一般（仅记录）。协调器必须带GUI/Web界面。 |

你们现在拥有的**多设备分布式视线检测**是一个非常巧妙的架构——它天然适合做多选项并行选择，而不是只能做"是/否"。这是很多单屏视线交互系统做不到的。建议充分利用这个优势，把交互层设计成"患者身边的多个可选项"，而不是"一台设备反复提问"。
